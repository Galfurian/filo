In the Codex sandbox, `filo send` to a registered session now says that the sandbox is the problem, and how to get past it.

**What is fixed**

- **A sandboxed sender is no longer told that a connected recipient is down (#81).** The Codex sandbox refuses every `connect()` to a Unix socket, whatever the path and whatever the config. A **listener** still gets the message as a file in its spool, but a **registered** session (Claude with an inbox socket, Codex, agy) has no spool: it is reached through a socket. filo took the refusal for a recipient that was not connected, so an agent told its user that the manager was down. The error now says `this sandbox cannot connect to sockets`, and that the recipient is a registered session. For a name that is not registered it says that the recipient is not connected, or that the sandbox cannot connect and filo cannot tell which.

**How to get past the sandbox**

Add one line to `~/.codex/rules/default.rules` and start Codex again; `filo send` then runs outside the sandbox, without full access for anything else:

```
prefix_rule(pattern=["filo", "send"], decision="allow", justification="filo send needs a Unix socket, which the sandbox blocks")
```

The README ("In the Codex sandbox"), `filo boot` for Codex and the skill say so. filo does not write to that directory itself: the rule is yours to add, once per user and machine.

**Upgrade**

`filo upgrade`, or the one-line install again. Listeners that are running keep the old code until they join again.

**Internal**

The tests of the sandbox case use a real socket with no permissions, which macOS refuses as Linux does (#81). Dependencies and actions are updated: CodeQL 4.39.1, `setup-python` 7.1.0, ruff 0.17.3, mypy 2.4.1, nodeenv 1.12.0 (#79, #80, #82, #83, #84).

**Security posture**

Unchanged from 0.6.0. `get.sh` and `SHA256SUMS` are signed with Sigstore and covered by the build provenance.
