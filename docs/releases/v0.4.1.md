Fixes for nine problems found in a review of 0.4.0, two of which lost a message that its sender had been told was delivered. If you use filo with a detached listener (the Claude setup), upgrade.

**Fixes**

- **A big message with non-ASCII text could be reported as delivered and then be lost.** A listener keeps what it receives in a file, and a sender leaves one in the spool when the recipient is away, with every non-ASCII character escaped, which takes up to six times the size of the message; a file above the size of one frame was refused. A message of 3 MB of Chinese text was "sent directly" and then `filo show` could not find it and `filo watch` never printed it; one that waited in the spool was deleted when its recipient came back. A file may now hold what a frame holds, escaped.
- **`filo send` refuses a message that is too big to carry** (about 4 MB of text) and says so, instead of falling back to a spool that would have thrown it away.
- **`filo watch` skipped a message whose id was older than the last one it printed.** An id is made by the sender before it delivers, so a slow sender, or the spool (every message from a sandboxed sender goes through it), could deliver a message after one sent later. It was saved and never printed. The cursor now says when a message was received, not which id it had; the cursor of an older filo is understood.
- **A bad adapters file stopped `filo who`, `filo join` and a message to a listener that was away**, for everyone, even with nobody registered, and `join` left its socket behind. The error is printed to stderr and the command goes on.
- **A name of 300 characters, a directory that had been removed, or a `--scope` too long to look up ended in a traceback.** Names are limited to 64 characters, and any remaining file system error is a one-line message with exit status 1.
- **`filo join --parent 0` made a listener that never ended**, because `kill(0, 0)` always succeeds. `--parent` must be above 0.
- **The listener wrote an acknowledgement file named after the id that a raw client of its socket sent**, so `../../x` wrote outside its directory and a long id made the answer an error after the message had been shown. It now does so only for an id that filo could have made. (It needs a process of your own user, which `SECURITY.md` puts out of scope; this is robustness.)
- **A spooled message was deleted before it was delivered**, so a listener that ended in between lost it. It is deleted after, so one that is cut short is delivered again (a message may repeat; one is never lost). A message that cannot be shown at all is still dropped, or the listener would fail on it at every start.
- **A delivery command was given every variable in the registration file**, not only the ones its adapter captures. It now gets only those (defence in depth: it takes a process of your own user to write the file).

**Also**

- Old acknowledgements are pruned once a minute, with the inbox, not twice a second by every listener.

**Changes in behaviour**

A name longer than 64 characters, a message of more than about 4 MB of text and a `--parent` of 0 or less are now errors; they did not work before, and failed late or not at all. Nothing else a user does changes.

**Upgrade**

`filo upgrade`, or the one-line install again. A session that was started before the upgrade runs the old version until it is restarted.

**Security posture**

Unchanged: `get.sh` is signed with Sigstore, covered by the build provenance and listed in `SHA256SUMS`, like the archive.
