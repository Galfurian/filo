`filo setup codex` lets `filo send` out of the Codex sandbox, so that a sandboxed Codex can reach a registered session.

**What is new**

- **`filo setup codex` (#86).** The Codex sandbox refuses every Unix socket, so a sandboxed Codex cannot send to a registered session (Claude with an inbox socket, Codex, agy). The way out is a rule that Codex reads when it starts. The command shows the line that it adds to `~/.codex/rules/default.rules` (or `$CODEX_HOME/rules`), asks first, copies the file to `default.rules.bak` and adds nothing twice. `--dry-run` shows it and changes nothing; `--yes` does not ask. Start Codex again afterwards.
- **`filo register` warns in a sandboxed Codex (#86).** Until the rule is there, it says that `filo send` will not reach a registered session and that the user has to run `filo setup codex`; in `--json` the line has a `warning`. An agent is told not to run the command itself.
- **`install.sh` says so when it finds Codex (#86).** It prints the suggestion and changes nothing in the configuration of Codex.

**What it changes, and what it does not**

The rule lets `filo send`, and no other command, run outside the sandbox without asking. `filo send` can only write to another agent of the same user on this machine. SECURITY.md says so. filo finds the rule by reading the `*.rules` files: a rule that Codex gets from somewhere else is not seen, and the warning is then a false alarm.

**Upgrade**

`filo upgrade`, or the one-line install again; then run `filo setup codex` on each machine where Codex runs in its sandbox, and start Codex again. A Codex that runs with full access needs nothing.

**Security posture**

`filo setup codex` is the one command that writes to the configuration of another program, and it asks first. Otherwise unchanged from 0.6.1: `get.sh` and `SHA256SUMS` are signed with Sigstore and covered by the build provenance.
