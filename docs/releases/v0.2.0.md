Install and upgrade filo without a checkout. This release is the first one that carries `get.sh`, so the one-line install works from here on.

**New**

- **One-line install and uninstall.** `get.sh`, attached to each release, downloads the release archive over https, checks its SHA-256, unpacks it into `~/.local/share/filo` (`FILO_HOME` changes that) and runs the `install.sh` inside, which says which links it makes before it makes them.

  ```sh
  curl -fsSL https://github.com/Galfurian/filo/releases/latest/download/get.sh | sh
  curl -fsSL https://github.com/Galfurian/filo/releases/latest/download/get.sh | sh -s -- uninstall
  ```

  Both take `--dry-run` (`sh -s -- --dry-run`, or download `get.sh` and run `sh get.sh --dry-run`). Uninstall deletes only a directory that holds the marker `get.sh` wrote, and refuses `/`, your home directory, a relative path and a link. `./install.sh` from a checkout works as before.
- **`filo upgrade`.** `filo upgrade --check` says whether a newer release exists, by looking where `/releases/latest` points. `filo upgrade` fetches the `get.sh` of that release, refuses it unless it is stamped for that version, shows its dry run, asks (or takes `--yes`) and runs it for the directory this filo runs from. A checkout is told to `git pull`; a copy that did not come from `get.sh` is refused.
- **An opt-in notice of a new release.** With `FILO_CHECK_UPDATES=1`, `filo who` looks at most once a day, for two seconds at most, and adds one line on stderr when a newer release exists. It is off unless you set it, silent when offline and never printed with `--json`. The skill tells agents to pass the notice on to you and not to run `filo upgrade` themselves.

**Behaviour to know about**

`filo upgrade` and the optional notice are the only places where filo uses the network; messages never leave the machine. `FILO_RELEASES_URL` accepts https only. `SECURITY.md` has a section on this.

**Security posture**

`get.sh` is stamped by the release workflow with the version and the SHA-256 of the archive, so a copy from a release can only fetch that archive; an unstamped copy refuses to run. It is signed with Sigstore (`get.sh.sigstore.json`), covered by the build provenance and listed in `SHA256SUMS`, like the archive. The hash and the archive come from the same release, so someone who can change a release can change both: check `get.sh` with the signature or the provenance first if that matters to you (`SECURITY.md`, "Checking a release").

The project is registered for the OpenSSF Best Practices badge, shown in the README.
