`filo ui` shows a pool in a browser, and filo now keeps what passes through it, so that the text of a message to a Codex, agy or Claude session is no longer lost.

**What is new**

- **`filo ui`: a pool in a browser (#57, #58).** It prints an address and shows who is in a scope and what they say to each other, live. There are two views. The **Board** gives each entity a box, the boxes fill the page and are laid out again when it is resized; when one entity writes to another an arrow is routed through the gaps between the boxes, from the sender to the recipient, and the message appears there. Each box says which client its entity runs under (`manager · claude · pid 1234`, `worker2 · codex · registered`), scrolls through its history and follows what comes while it is at the bottom, and a button opens a sheet with the whole conversation of that entity, in both directions, with a filter by who it talks with and a search. A Codex session whose client holds messages for it shows how many and for how long (`9 waiting · 47 min`). The **Log** is the same flat list in time order. Light or dark follows the browser. It is one small page served by the standard library: nothing to install and nothing fetched from the web.
- **A log of each scope, `events.jsonl` (#56).** `send` keeps every message with its sender, recipient, id, state and text (cut at 20,000 characters), and joins, registrations and leaves are kept too: for a day, in mode `0600`, up to `FILO_LOG_LIMIT` bytes (4 MB by default). `FILO_NO_LOG=1` turns it off. It is what the viewer follows, and the only place that holds the text of a message to a client that has no listener: until now filo handed it to the client's queue and kept only an acknowledgement.
- **The viewer shows a pool that does not have the log yet (#58).** From what an older filo kept (what its listeners received in the last day, and the acknowledgements of what was handed to a client's queue, which have no sender and no text), so that it is useful at once on a pool that runs an older filo.
- **A listener records the client it runs under (#58).** From the variable that the client sets in the shell of its sessions (`CLAUDECODE`, `CODEX_THREAD_ID`, the one of agy), or from `FILO_CLIENT`, which the OpenCode plugin sets. `filo who --json` has it as `client`; a listener started before has none.

**Changes in behaviour**

- `send`, `join`, `register` and `leave` now write to the log of the scope (a best effort that never stops them). It holds the text of the messages, as the inbox of a listener already does for what it received. SECURITY.md and the README say so.
- Participants in `who --json` have `client` (null when it is not known).

**Upgrade**

`filo upgrade`, or the one-line install again. The `filo` command that each agent runs is the installed one, so what it sends is kept in the log from the next message on. A listener that was started before runs the old version until it joins again (`filo who` says which). Then `filo ui` in the directory of the pool, and open the address.

**Security posture**

The viewer listens on `127.0.0.1` only, answers only to the token in its address (then an `HttpOnly`, `SameSite=Strict` cookie) and to its own host name, only for a scope that filo knows, with a policy that lets only the page's own script run, and it puts what comes from the pool in the page as text and never as markup; it writes nothing. The log holds the text of messages for a day, in a file of mode `0600`. Otherwise unchanged from 0.4.6: `get.sh` and `SHA256SUMS` are signed with Sigstore and covered by the build provenance.
